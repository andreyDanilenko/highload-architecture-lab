# Первые 30 задач: оценка качества постановок и материалов

Дата: 2026-09-24. Оценка относится к описаниям задач, связям между ними и пригодности для небольших экспериментов. Это не новый аудит всех реализаций и не подтверждение готовности к эксплуатации. У 01–04 есть код разной полноты; 05–30 в текущем репозитории представлены планами.

Основной результат этой работы — [ссылки на материалы и реальные проекты по каждой задаче](reading-map-01-30.md). Читать их можно по интересу и возвращаться к ним после изменения кода. [Карта EventLab и мастерских](project-playground-01-107.md) показывает необязательные способы соединения всех 107 тем.

## Общая оценка

**Набор тем полезен для разборов:** через него видны состояние, конкуренция, повтор, отказ, стоимость хранения, сетевые границы и наблюдаемость. Главный недостаток — некоторые названия обещают гораздо больше, чем один понятный опыт. Добавление новых технологий само по себе не улучшает задачу; полезнее один видимый сценарий и возможность заменить реализацию.

| Критерий | Оценка текущих материалов | Что уточняется этой подборкой |
|---|---|---|
| Связь с практикой | Сильная у повторов, БД, ограничения ресурсов, наблюдаемости | Ссылки на авторскую документацию, инженерные объяснения и исходный код |
| Понятность входа | Неравномерная: много названий паттернов, мало маршрутов чтения | Для каждой темы указано, что открыть и какой вопрос посмотреть |
| Размер опыта | У части задач слишком широкий | Предлагается минимальный сценарий без требования повторить целый промышленный продукт |
| Границы гарантий | В README уже уточнены многие обещания; некоторые названия всё ещё шире содержания | Отдельно отмечены Kafka/external effect, lease/fencing, кэш/свежесть, Merkle/доверенный корень |
| Связность | Прежний plan переключался между разными предметными областями | EventLab даёт постоянный пример, другие мастерские доступны независимо |
| Повторяемость тем | Полезная, если понятно новое условие | Явно разделены 02/05, 07/08, 04/21, 23/28 |
| Читаемость Go | Нельзя оценить по числу папок и интерфейсов | Разбор одной ветки и одного запроса, небольшой фрагмент за раз |

Числовой «балл качества» здесь не вводится: нет измеренной шкалы, а сила темы и готовность реализации — разные вещи.

## Оценка каждой задачи

«Сохранить» означает удачную тему для опыта; «сузить» — выбрать небольшой первоначальный объём; «развести» — явно отделить от соседней темы. Это решения по постановке, а не отметки прохождения.

## Как отбирались ссылки

- Приоритет у авторов технологии: официальная документация, оригинальная статья, репозиторий проекта или инженерный материал организации о своей системе.
- EN/RU — язык страницы, а не оценка качества. Русская локализация может отставать; если она объясняет только часть темы, это подписано.
- Документация отвечает «каков контракт», инженерная статья — «почему выбрали решение», исходный код — «как устроена конкретная реализация». Одно не заменяет другое.
- Учебный проект и промышленная библиотека сравниваются по выбранному механизму, не по размеру репозитория или числу звёзд.
- Проверка ссылки означает, что найдено содержимое по указанной теме. Она не означает, что проект запускался, проходил аудит безопасности или подходит для любого окружения.

Подробности проверки сохранены в [реестре источников](sources-01-30.json). У каждой задачи в [карте чтения](reading-map-01-30.md) есть собственное замечание о покрытии и возможный маленький опыт.

## Что исправить при следующем изменении постановок

Сначала уточнять названия и минимальный объём 08, 09, 21, 25 и 27. Сохранять темы и номера, чтобы старые ссылки и наблюдения оставались понятными. У задач 01–04 не переписывать результаты прошлых запусков под новую формулировку. У 05–30 добавлять запускаемый пример по мере интереса, а не создавать сразу 26 пустых сервисов.
