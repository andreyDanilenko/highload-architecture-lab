# Задача 04: контракт идемпотентности

Документ описывает текущую Go-реализацию. Запуск и фактические проверки — в [README задачи](../../README.md) и [записной книжке](../experiment-notes.md). Сценарии ниже — ожидания для проверки, а не результаты проведённых запусков.

## Вопрос опыта

Сравнить `noop`, `memory`, `redis` и `advanced` за общим HTTP middleware. Разделить три события: допуск попытки, учебный бизнес-эффект и сохранение ответа. Ни один провайдер не объединяет их в одну транзакцию.

`POST /api/v1/payments` принимает один JSON-объект:

```json
{"from":"account-a","to":"account-b","amount":100}
```

`amount` — положительное целое `int64` в минимальных денежных единицах. Аккаунты непустые, разные, не длиннее 128 байт. Неизвестные поля, дополнительный JSON, дробная сумма и некорректная операция отклоняются. Сервис записывает имитацию эффекта: реальные деньги не переводятся, балансов счетов нет.

## Идентичность запроса

- Ровно один `Idempotency-Key`: 1–128 видимых ASCII-байт без пробелов.
- Необязательный `X-Demo-Tenant`: 1–64 таких же байт; значение по умолчанию `lab`. Это демонстрация scope, а не аутентификация арендатора.
- Ключ хранилища — SHA-256 от метода, совпавшего шаблона маршрута, tenant и клиентского ключа с однозначными разделителями.
- Fingerprint — SHA-256 конкретного escaped path, исходной query-строки и исходных байт тела, без нормализации. Изменение path-параметра, query, пробелов или порядка JSON-полей даёт конфликт при том же scope/key, пока запись существует.
- Размер тела проверяется до захвата. Аутентификация, канонизация JSON, нормализация query и другие заголовки в контракт идентичности не входят. Значения wildcard path-параметров входят в fingerprint, не в scope: другое значение при том же шаблоне маршрута/ключе конфликтует, а не получает независимый ключ.

## Порт хранения

В [provider.go](../../go/pkg/idempotency/provider.go) объявлены:

```go
Acquire(ctx context.Context, key, fingerprint string, lease time.Duration) (Claim, error)
Complete(ctx context.Context, key, owner string, response Response, retention time.Duration) error
Name() string
```

`Claim` содержит либо owner token новой попытки, либо сохранённый ответ. Stateful-провайдеры проверяют владельца в `Complete`. Это защищает запись от чужого завершения, но не является fencing, проверяемым бизнес-эффектом.

| Стратегия | Допуск и replay | Истёкший незавершённый lease |
|-----------|-----------------|-----------------------------|
| `noop` | Каждый запрос вызывает handler; проверки fingerprint и replay нет | Записи нет |
| `memory` | Map под mutex, предел числа записей, копии ответа | Запись остаётся; unknown, без нового владельца |
| `redis` | `SET NX` с TTL pending; `WATCH`/транзакция при завершении | Запись исчезает; следующий запрос может повторить эффект |
| `advanced` | Lua проверяет состояние/owner; lease по времени Redis | Pending без TTL; unknown, без нового владельца |

Завершённый ответ у stateful-провайдеров хранится `ResultTTL` от момента завершения. После истечения этого срока тот же ключ может снова выполнить операцию. `memory` действует внутри процесса. Redis-стратегии координируют только экземпляры с общим Redis и namespace. Для разных стратегий и независимых опытов задавать разные `-redis-prefix`; смешивать реализации в одном namespace нельзя.

## Последовательность HTTP

1. Проверить ключ, demo tenant и размер тела; вычислить scope и fingerprint.
2. Получить допуск, готовый ответ или ошибку провайдера.
3. Выполнить handler в ограниченный буфер ответа.
4. Передать статус, байты тела и только `Content-Type`/`Location` в Complete. Контекст завершения отделён от отмены клиента, но ограничен `CompleteTimeout`; noop намеренно ничего не сохраняет.
5. Отправить буферизованный ответ клиенту. При ошибке сохранения не выдавать буферизованный бизнес-ответ как успешно сохранённый.

Stateful-провайдеры сохраняют завершённые ответы handler, включая обычные 4xx/5xx. Тот же ключ/тело воспроизводит ошибку до expiry retention, а исправленное тело конфликтует, пока запись существует. Потоки, cookies, произвольные заголовки и неограниченное тело не поддерживаются. Panic и переполнение буфера оставляют попытку незавершённой.

| Ситуация | HTTP-результат |
|----------|----------------|
| Неверный/отсутствующий ключ или demo tenant | 400 |
| Тело запроса превышает лимит | 413 |
| Попытка ещё активна | 409 `in_progress`, `Retry-After: 1` |
| Тот же scope/key с другим path, query или телом | 409 `key_mismatch` |
| Провайдер сообщает неизвестный исход/истёкшее владение | 409 `outcome_unknown` |
| Хранилище недоступно или memory достиг capacity | 503 `idempotency_unavailable` |
| Ошибка Complete или переполнение буфера ответа | 503 `outcome_unknown` |
| Panic handler | 500 `outcome_unknown` |

Неизвестный исход не означает отсутствие эффекта. Новый клиентский ключ обходит прежнюю запись и не является протоколом восстановления.

## Наблюдение и конфигурация

`GET /api/v1/effects` возвращает `{count, payments}` из ограниченного журнала в памяти процесса. Журнал намеренно не дедуплицирует. При нескольких экземплярах читать журнал каждого. Рестарт теряет журнал; ID транзакций локальны. Поэтому журнал не доказывает восстановление устойчивого эффекта после падения. В Redis может сохраниться ответ, хотя журнал соответствующего процесса уже потерян.

`GET /metrics` публикует фиксированные outcome labels и сумму/число длительностей, без квантилей. `GET /healthz` проверяет Redis для Redis-стратегий. Это учебные средства наблюдения без аутентификации.

CLI: `-provider noop|memory|redis|advanced`, по умолчанию `memory`. Основные defaults: `-lease-ttl 30s`, `-result-ttl 24h`, `-complete-timeout 2s`, лимиты запроса/ответа 65536 байт, `-max-entries 10000`, `-payment-delay 0`. Допустимая задержка — 0–10s; capacity ограничивает memory-провайдер и журнал каждого процесса. Все флаги: `go run ./cmd/server -help` из `04-idempotency/go`.

## Границы и контрпримеры

Проверить replay без нового эффекта, конфликт path/query/тела, выполнение дольше lease, завершение устаревшим owner, expiry завершённого результата и потерю данных. Записать предположения и фактические наблюдения отдельно.

В `advanced` истёкший pending остаётся в карантине до выяснения исхода. API сверки, продления lease и административного разрешения неизвестного исхода не реализованы. Eviction, удаление или потеря Redis-записи снимают эту защиту. Атомарность Lua не охватывает внешний эффект.
