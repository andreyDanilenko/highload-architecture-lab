## Что такое идемпотентность (фундаментально)

**Идемпотентность** — это свойство операции, при котором **однократное и многократное применение дают одинаковый результат и одинаковый побочный эффект**.

Формула:
> `f(f(x)) = f(x)`

**Простой пример:**
- `set(x, 5)` — идемпотентно (сколько раз не ставь 5, результат 5)
- `increment(x)` — **не** идемпотентно (каждый раз число увеличивается)

## Идемпотентность в контексте HTTP API

В нашем случае проблема глубже. Нам нужно сделать **неидемпотентную бизнес-операцию** (списать деньги) **внешне идемпотентной** для клиента.

**Классический сценарий:**

```
Клиент → Банк: "Списать 100$" (запрос А)
Банк → Клиент: (ответ потерялся в сети)
Клиент: "Я не получил ответ, отправлю повторно" (тот же запрос А)
```

**Без идемпотентности:** 200$ списано (дважды)
**С идемпотентностью:** 100$ списано (один раз), но клиент получает ответ (либо старый, либо новый)

---

## Ключевое отличие: HTTP-методы ≠ идемпотентность

Часто путают идемпотентность HTTP-методов с идемпотентностью бизнес-операций.

| HTTP-метод | По спецификации | Реальность |
|------------|-----------------|------------|
| `GET` | Идемпотентный | Но если на бэкенде `GET` увеличивает счетчик — нет |
| `PUT` | Идемпотентный | Только если клиент отправляет полное состояние |
| `POST` | Не идемпотентный | Поэтому для платежей используют `POST` + `Idempotency-Key` |

**Вывод:** Мы не можем полагаться на HTTP-метод. Нужен **механизм уровня приложения**.

## Идемпотентность в контексте задачи 4

В этой задаче мы строим **слой**, который превращает любую неидемпотентную операцию в идемпотентную.

### Архитектурная модель

```
[Клиент]
   │
   │ POST /payments
   │ Idempotency-Key: uuid-123
   ▼
[Idempotency Middleware]  <-- ЭТО МЫ СТРОИМ
   │
   │ 1. Проверить: был ли уже ключ uuid-123?
   │    - Был → вернуть сохраненный ответ
   │    - Не был → создать запись "pending"
   │
   ▼
[Business Logic]  (неидемпотентная: списать деньги, отправить email)
   │
   │ Выполняем операцию 1 раз
   │
   ▼
[Idempotency Middleware]
   │
   │ Сохранить результат (успех/ошибка) по ключу uuid-123
   │
   ▼
[Клиент]
```

### Жизненный цикл idempotency-ключа

```
СОСТОЯНИЯ:
                    ┌─────────────────┐
                    │      NEW        │ (ключа нет в хранилище)
                    └────────┬────────┘
                             │ первый запрос
                             ▼
                    ┌─────────────────┐
                    │    PENDING      │ (операция выполняется)
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │  SUCCESS   │  │  FAILURE   │  │   TIMEOUT  │
     │ (200-299)  │  │ (4xx-5xx)  │  │  (lock     │
     └────────────┘  └────────────┘  │   expired) │
                                      └────────────┘

ПОВТОРНЫЕ ЗАПРОСЫ:
- Если SUCCESS/FAILURE → возвращаем сохраненный ответ (кэш)
- Если PENDING → возвращаем 409 Conflict (или ждем)
- Если TIMEOUT → пытаемся забрать lock или создать новую операцию
```

## Фундаментальные принципы, которые ты вынесешь

### 1. Ключ идемпотентности должен генерировать **клиент**

Почему:
- Сервер не может отличить повторный запрос от нового, если оба пришли без ключа
- Клиент знает, что он уже отправлял этот запрос (даже если не получил ответ)

**Плохо:**
```http
POST /payments
{"amount": 100}  // без ключа — нельзя отличить повтор
```

**Хорошо:**
```http
POST /payments
Idempotency-Key: 8e7b3f2a-1c4d-4e8f-9a2b-5c6d7e8f9a0b
{"amount": 100}
```

---

### 2. Идемпотентность ≠ транзакционность

Важное различие:

| Свойство | Что значит | Пример |
|----------|------------|--------|
| **Идемпотентность** | Повторные вызовы не меняют состояние после первого | `update user set name = "John"` |
| **Транзакционность** | Операция либо полностью выполняется, либо полностью откатывается | `BEGIN; UPDATE ...; COMMIT;` |

**Нам нужно и то, и другое:**
- Идемпотентность — чтобы повторные запросы не вредили
- Транзакционность — чтобы операция не выполнилась наполовину

В задаче 4 мы строим идемпотентность **поверх** транзакционности бизнес-логики.

---

### 3. Проблема "pending" и конкурентных запросов

**Сценарий:** Клиент отправил запрос с ключом `X`. Сервер начал выполнять операцию (статус `pending`). Клиент не дождался ответа и отправил **второй** запрос с тем же ключом `X`.

**Вопрос:** Что делать?

| Стратегия | Поведение | Плюсы/минусы |
|-----------|-----------|--------------|
| **Ждать (блокировка)** | Второй запрос ждет завершения первого | Просто, но может зависнуть навсегда |
| **409 Conflict** | Сразу ответить "уже в обработке" | Честно, клиент знает что делать |
| **Retry-After** | 409 + заголовок `Retry-After: 5` | Клиент может подождать |

**Выбор в задаче:** Рекомендуется `409 Conflict`. Это прозрачно и не создает блокировок.

---

### 4. Проблема lock expiry (продвинутая)

**Сценарий:** Сервер начал выполнять операцию с ключом `X`, но завис (сломался, таймаут, сеть). Lock на ключе `X` висит.

**Вопрос:** Что делать через N секунд?

**Решение:** lock должен иметь TTL (например, 60 секунд). Если операция не завершилась за это время:
- Lock автоматически снимается
- Следующий запрос с ключом `X` может начать новую операцию

**Но:** Нужна осторожность. Если операция все-таки завершится после истечения lock, нужно:
- Игнорировать результат (операция "orphaned")
- Логировать для аудита

## Идемпотентность в фундаментальном программировании

В более широком смысле идемпотентность — это **паттерн работы с неопределенностью**.

### Где еще используется:

1. **Message brokers (Kafka):**
   - Продюсер может отправить сообщение дважды
   - Консьюмер должен быть идемпотентным

2. **Database migrations:**
   - `ALTER TABLE ADD COLUMN IF NOT EXISTS` — идемпотентная миграция
   - Можно применять много раз без ошибок

3. **Kubernetes manifests:**
   - `kubectl apply` — идемпотентная операция
   - Описываем желаемое состояние, система приводит к нему

4. **Функциональное программирование:**
   - Чистые функции по определению идемпотентны
   - `f(x)` всегда возвращает одно и то же

## Что ты должен вынести из задачи 4

### Техническое:
- Как строить middleware для идемпотентности
- Atomic операции в Redis (Lua, SET NX, WATCH)
- Обработка конкурентных запросов
- Graceful handling lock expiry

### Фундаментальное:
- Идемпотентность — это **контракт между клиентом и сервером**
- Ключ идемпотентности — это **идентификатор запроса**, а не операции
- Сервер хранит **ответ**, а не только факт выполнения
- Повторные запросы должны получать **тот же ответ**, а не просто "успех"
- Pending-состояние требует специальной обработки (lock, конфликт)

### Для архитектуры:
- Идемпотентность — это **первый шаг к event sourcing**
- Понимание разницы между "executed once" и "result is cached"
- Как строить надежные API поверх ненадежных сетей

## Итог

Идемпотентность — это **не просто кэширование ответов**.

Это **архитектурный паттерн**, который позволяет:
- Строить надежные системы поверх ненадежных сетей
- Гарантировать бизнес-инварианты (дважды не списать)
- Делать систему устойчивой к повторам и ретраям

**Задача 4** дает тебе этот инструмент. После нее ты сможешь проектировать API, которые можно безопасно ретраить, — а это 80% production-надежности.
